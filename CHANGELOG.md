# Changelog

All notable changes to this project will be documented in this file.

## Unreleased

### Added
- An automatic send now outlasts a silent attachment upload (widget 0.0.94). The live 2026-10-04 acceptance caught the exact failure the operator complained about: ChatGPT kept Send disabled for ~4 s with NO busy tile while it registered the prepared START attachment, the shared readiness wait gave up after its 1.4 s idle exit (the "fast failure is the point" contract, correct for a dead composer), and a START that must need nobody told the operator to press Send by hand. `triggerSend` and `recoverArmedStartSend` now wait out their own bounded budgets (12 s, 30 s with attachment delivery) before any fallback whenever a send control EXISTS but is disabled -- exactly the W6-009 patience the manual ZIP path already had; a MISSING control keeps the fast T-260 form-submit path; the "Press Send manually" notice now states that bounded recovery is retrying automatically. Proven red-then-green in `tests/widget/w6-009-manual-zip-send-patience.test.js` (the red control reproduced `mode=manual-only` on a silent upload).
- The widget can now name the layer that lost a live Core (widget 0.0.92). This release fixes NOTHING in the A3 lineage: the 2026-10-03 live acceptance of 0.0.91 failed again, and the repair is deliberately not shipped yet because the failing layer has not been proven from the live page. What shipped is the instrument. `superCompactAutoLabel()` can only reach `BUSY` while generating when BOTH the live lineage scan AND the runtime stage fail to name a wave, so `BUSY` is a symptom with four distinct causes, and repairing the wrong one burns a release on code the browser never ran: **A `TURN_DISCOVERY`** — the Core is on screen and `getChatGPTTurns()` never returned it; **B `TURN_CLASSIFICATION`** — the turn was returned and `classifyAuditTurn()` did not read it; **C `RUNTIME_ADOPTION`** — it is recognized and owned, and the runtime never adopted anything; **D `START_ROUTE_OWNERSHIP`** — a committed START cannot prove it owns the current `/c/<id>`. `liveAuditLineageSnapshot()` reads all of that off the live DOM — generation verdict, runtime stage, START handoff phase and route binding, turn counts, the latest authored turn's structural shape, its classified kind, the transaction-boundary candidate count — and `classifyLiveAuditLineage()` reduces it to exactly one class. It is CONTENT-FREE by construction: no prompt text, no conversation text, no receipt value, no tokens. That matters because the snapshot is rendered where the operator can read it: the compact cell's tooltip (only while ChatGPT is generating) and the Bridge diagnostics block behind **Copy diagnostics log**. No CDP, no debugging port, no new dependency — the userscript is already executing inside the exact page that must be diagnosed. One honest correction to the earlier framing: **C and D are not `BUSY` causes.** A Core that `liveAuditActivitySnapshot()` already recognizes renders `CORE`, so those two fail behind a *correct-looking* label while the runtime behind it owns nothing; the classifier reports them anyway, because the visible symptom is exactly what would hide them. `tests/widget/w7-013-live-lineage-snapshot.test.js` encodes the reproduction (A3 enabled, real composer, real current-build Stop, Core on screen, generating) and asserts all four classes separately, that a healthy lineage reports none, and that the serialized snapshot contains neither the receipt value, nor `AUDIT CORE`, nor `PROJECT_NAME`, nor any body text.
- SAI Accounts federation — the control plane is OPTIONAL, and AUDAPACK is complete without it. `audapack/sai_accounts.py` reads the shared account registry when the plane is installed, and `account_registry.discover_accounts()` folds those accounts in as `discovery_source="sai_accounts_shared"` rows in a `<provider>:shared:<digest>` id namespace that can never collide with a local one. STANDALONE (no plane) returns exactly the rows it always did; FEDERATED adds the shared accounts; HYBRID keeps local-only accounts and merges a shared row into a local one **only** on a proven identity locator — the config-directory path for Claude/Codex, the Windows account name for Antigravity, whose data root is shared by every user on the machine and therefore cannot identify an account. A display name is never evidence: unprovable identity leaves both rows standing. A shared account with no locator at all is still shown, marked shared and merged with nothing, rather than dropped — losing an account identity silently is worse than admitting it is unprovable. `AntigravityLimitAdapter` reads a shared account **through the plane**, never through `agy -p /usage`, which answers about whoever is logged in here: a shared row whose source is unavailable reports `shared_source_offline` / `offline:…` / `auth_required:…` / `unavailable:…` instead of borrowing another account's numbers. A provider the plane does not yet broker answers `provider_does_not_support_quota`, which is treated as an honest no-opinion, not an outage. Launcher bindings and the per-account enable flag stay local; global hide/disable in the shared registry is a separate concept. Everything here is read-only — the plane is asked for account metadata and nothing else, and no credential material is read, copied, exported or written. `tests/test_sai_accounts_federation.py` covers STANDALONE, broken plane, FEDERATED, HYBRID, duplicate discovery, central failure and the read-only guarantee (53 assertions); `tests/conftest.py` neutralizes the seam for the whole session so an installed plane can never leak real accounts into a fake-HOME test, the same way the Qt platform and the browser spawn are neutralized.
- Audit replies are captured automatically (widget 0.0.70). When a ChatGPT reply that the widget watched stream finishes, and the user message it answers carried a project ZIP, the reply is saved to the INAUDIT Inbox with no `IA` click. The widget sends the archive name with the capture, and the Bridge pins the capture to the one registered project that owns that archive name (same anchored match as archive lookup, so `_SAIPEN_Bar.zip` never claims `_SAIPEN`). The row then waits in the Inbox under the right project for **Assign** / **Assign + CC**. Short replies (under 1,200 characters), replies to messages without an archive, old conversations being reopened and worker-driven audit runs are skipped; the dispatcher already files worker-driven runs. Settings → Bridge → "Auto-capture audit replies to INAUDIT" turns it off. The opt-in "...and assign it to the project audit inbox" (off by default) also runs the Inbox **Assign** step for a pinned reply. The reply then goes straight to that project's audit inbox; for SAIPEN projects this is `saipen audit enqueue`. If the assignment fails, the capture stays in the Inbox and the widget says so.
- SAIHANDOFF blocks are filed automatically (widget 0.0.66). When a ChatGPT reply that the widget watched stream finishes with a handoff code block — one carrying a `SAIHANDOFF` marker, or a brief whose first line is a registered project's name (`LIMISAW` / `MISSION` / ...; the Bridge decides, so an ordinary code block is never filed) — the block is captured through the existing INAUDIT pipeline as `capture_kind: handoff`, and the Bridge writes it byte-exact as `<Project>_<YYYYMMDD>_<HHMM>.md` (the scratchpad-export naming) into `bridge.handoff_dir` (default `%TEMP%\audapack_handoffs`). The file path is copied to the clipboard, so handing the brief to an agent is one paste. The same block always resolves to the same file; opening or scrolling an old conversation never re-files its handoffs; the manual block-capture button also produces the file. Settings → Bridge → "Auto-save SAIHANDOFF blocks" turns it off.
- `Probe GET` in the widget's Bridge diagnostics times a content-free, archive-sized download through Tampermonkey and through native `fetch` (cold and warm) against the new token-free `/v1/probe/bytes` endpoint, and records the comparison in the mirrored diagnostics log. Native fetch never receives the Bridge token; archive delivery stays on `GM_xmlhttpRequest`.

### Fixed
- The A3 lineage failure 0.0.92 deliberately left open is closed: the widget can see the Core the current ChatGPT build actually renders, and a managed Core no longer reads `BUSY` while it is running. 0.0.92 shipped only the instrument, because the failing layer had not been proven from the live page — and that proof is what the next CDP session on the dedicated AUDAPACK profile produced (dispatch `dsp-fc76adbfbfc649e7`, FastPrompter quick3, one managed worker). Every transport stage of that run worked and the run still never advanced: for minutes every diagnostic read `lineage=TURN_DISCOVERY reason=no-user-turn-discovered turns=0(u0/a0)` over a conversation that plainly held a 5099-char authored Core carrying `ACB_CHAIN_RECEIPT`. The cause was an ordinary DOM bug, not an external blocker. A whole-conversation census inside `WorkspaceContent` found **zero** of the three shapes `getChatGPTTurns()` knew — `[data-turn]`, `[data-testid^="conversation-turn-"]`, `[data-message-author-role]` — because the 2026-10 build renamed every one of them. The replacement shapes are `[data-chatgpt-search-message-ids]` (one per message, in document order, and the turn container), `[data-user-message-bubble]` (marks the user half), `[data-conversation-role="assistant"]` (names the answer half) and `[data-chatgpt-selection-message-id]` (the answer's own id). `[data-turn-key]` is the CONVERSATION id and appears once per thread, so it is deliberately never read as a turn: doing so collapses both halves of an exchange into one node. `CHATGPT_CURRENT_TURN` is appended LAST in the stable selector list, so a page still rendering the historic shapes is read exactly as it was before, and the `PERF-006` single-lookup budget is untouched for every node that still resolves by attribute. Why `BUSY` and not a wrong wave: `superCompactAutoLabel()` can only answer `BUSY` while generating when BOTH the live lineage scan AND the runtime stage fail to name a wave, so a reader that returns nothing takes away the only evidence the runtime had left to adopt with — no lineage, no `wait-<wave>`, no `Bridge AUDITING`, and a cell reading `BUSY` over an audit that is demonstrably running. Nothing else changed shape: there is no second adoption path and no parallel state machine, `reconcileEnabledIdleAuditRuntime()` / `resumeRuntimeFromAuditTurn()` remain the single runtime-adoption authority, and generation stays liveness rather than lineage identity. Ordinary non-audit generation still reads `BUSY`, deliberately — the fix adopts a Core it can actually SEE, not every conversation that happens to be generating. `tests/widget/w7-014-current-build-turn-discovery.test.js` carries the measured DOM verbatim (4 cases) and `tests/widget/w7-016-managed-core-busy-lineage.test.js` asserts the operator's own description end to end (6 cases): the reader sees the Core, the classifier no longer reports `TURN_DISCOVERY`, the cell reads `CORE` in both managed stages (`await-core-user` and `wait-core`) AND over a runtime that has gone blank to `idle` with the Core still on screen, and an ordinary question still reads `BUSY`. Both files were proven red against the pre-fix reader before this repair: removing only `CHATGPT_CURRENT_TURN` fails 6/6 and 4/4.

The live reproduction was not a Send failure: ChatGPT received the Core and started generating, and AUDAPACK never adopted it. The compact cell read `BUSY`, the expanded panel read "Armed. Waiting for a NEW AUDIT CORE.", the archive line read "none attached to this audit", and the Bridge lane read `AUDITING` — over a runtime sitting at `stage: idle`. Three separate facts were represented by one boolean: submission attempted, payload left the composer, and the machine-authored user turn registered. `chatGPTSendAccepted()` treated a live generation Stop as acceptance, so a Start send returned `true` with **zero** user turns and the Core still sitting in the composer; `startAuditCoreFromReadyAttachment()` then discarded `recoverSentStartCore()`'s answer and returned `true` regardless, and `browserWorkerConsume()` read that as a successful START. Generation now stays what it always was — proof that ChatGPT reacted — and is no longer proof of which user turn owns the audit lineage. `chatGPTSendOutcome()` reports `{ submitted, payloadDeparted, generating, userTurnRegistered, userTurnId, receiptVisible, state, reason }` with `REJECTED` / `SUBMITTED_UNREGISTERED` / `REGISTERED`; `chatGPTSendAccepted()` is kept unchanged as the transport verdict for the manual and fallback send paths, which only ever needed "did the payload leave". A committed Send whose turn has not hydrated is now an explicit runtime stage — `await-<wave>-user`, the generic contract the second and third waves already used — instead of `idle`, so the panel says "Core submitted; waiting for ChatGPT to register the authored turn." and the compact cell reads `CORE`. `Bridge AUDITING` is now a claim about local ownership: it is crossed only when the runtime holds a concrete `wait-<wave>` stage, in `browserWorkerConsume()` and in the poll-side re-assert alike, and a `STARTED` lane whose window has not adopted its Core stays `STARTED` and is promoted the moment adoption lands rather than lying about an audit that is harvesting nothing. `startAuditCoreFromReadyAttachment()` returns `{ sent, adopted, state, reason, receipt, turnId, stage, runId }` instead of a bare `true` that meant both "the message left the composer" and "the Auto3 engine owns the Core". A self-authored Core is adopted by TRANSACTION BOUNDARY, not by re-parsing its own multi-thousand-word prompt out of ChatGPT: the pre-send user-turn baseline, the campaign run, the project, the archive identity, the profile and the receipt are captured at the `beforeSend` hook, immediately before the one irreversible click, and the single new user turn after that baseline is the committed Core even when ChatGPT renders only a clamped subset behind "Show more" and the trailing receipt is unreadable. The exact machine receipt stays the strongest evidence, DOM prompt parsing remains the fallback for manually authored audits and foreign/reload adoption, and two fresh user turns after the baseline fail closed into a named `ATTN` rather than binding a human message to this audit's lineage. A late route recovery (`draft:` → `/c/<id>`) no longer replaces the committed START snapshot with a freshly created blank destination runtime: one explicit merge policy carries `runId`, profile, project, project id, archive name/size/timestamp and the Core transaction across, and a destination that already owns real audit state is never degraded by a poorer source. Because the composer attachment naturally disappears on submission, archive status now reads from that durable runtime transaction, so the expanded panel keeps reporting the project archive that started the audit. The panel's `SAIHANDOFF IDLE` line is now `Implementation handoff: IDLE` with a tooltip naming the subsystem — that M1 archive/send automation is not the Auto3 audit chain — so a live Core is no longer visually described as idle by a neighbouring field. `tests/widget/w7-012-core-turn-registration.test.js` keeps the exact current-red control asserted: a Core and its receipt still in the composer, zero user turns, a real generation Stop mounted, `chatGPTSendAccepted(...) == true` and `chatGPTSendOutcome(...).state == 'SUBMITTED_UNREGISTERED'`. It also covers the clamped long Core, the pre-baseline turn, competing human turns, the Bridge contract, route-migration identity, archive-after-send and compact/full consistency.
- The audit payload is submitted even when the site renames its Send control (widget 0.0.90). The widget attached the archive, authored the exact AUDIT CORE text, and never sent; the operator pressed Send by hand. - The compact widget can no longer read READY over a generation signal it could not identify (widget 0.0.88). After 0.0.86 an operator still saw a visibly generating A3 audit tab with wave indicators lit and the cell reading READY, and the failure was unauditable from outside: the managed worker opens no debugging port, and the installed userscript reports its `@version` nowhere in the UI, so "stale build" and "detector out of date" looked identical. Two things follow from that. The generation verdict is deliberately unchanged (an unverified control never becomes generation, so 0.0.85's stall stays closed), but `superCompactAutoLabel()` may no longer return READY over that disagreement: it returns `ATTN`, which is honest and actionable, and it never sends, commits a wave or stands a worker down. The veto covers only READY, so a finished Core still reads `CORE`. Second, the compact cell's tooltip now carries the installed build and the live generation verdict — `AUDAPACK Widget 0.0.88 - generation: generating (canonical-stop-owned, saw canonical-stop-current-build)` — so a stale tab and a stale detector can be told apart in one hover instead of one debugging session. The voice exclusion also gained the words it was missing: `Stop listening` and `Stop recording` contain neither "voice" nor "microphone", so every dictation teardown button was a stop-shaped candidate the widget already called non-generation; it is now excluded by name, which keeps a dictating operator off ATTN. `tests/widget/w7-010-ready-generation-veto.test.js` covers the veto, the out-of-composer case, the four voice/dictation shapes, the 0.0.85 sibling-shell regression and the completed-Core case.
- A live generating ChatGPT tab no longer reads READY (widget 0.0.86). 0.0.85 stopped the false positive by tightening the generation identity to three exact markers, and in doing so dropped the marker the current chatgpt.com build actually ships. Captured live on 2026-09-29 mid-generation, the real control is `<button type="button" aria-label="Stop">` — no `data-testid`, no `id`, no `role` — sitting in the trailing action slot of the composer `<form class="relative flex flex-col gap-2">` (that form carries no `data-type`), beside a **disabled** Dictate and the model picker, with an `svg.icon-primary-action` child carrying the square glyph. Ownership was never what rejected it: `chatGPTStopNearComposer()` accepts `root.contains()`, and this control is inside the current composer form. Two independent audit tabs (FastPrompter and AUDAPACK) each showed a live assistant status and the orange Stop-square control while both widgets read `READY`. `button[aria-label="Stop"]` is admitted again, exactly: the exclusion of voice, dictation, media, conversation-turn and response-action surfaces still keeps an exact `Stop` anywhere else on the page out of the verdict, so the 0.0.85 fix is preserved. The diagnostic names the control `canonical-stop-current-build`, and `tests/widget/w7-009-current-stop-control.test.js` encodes the captured DOM — the generating Core, the non-audit chat, a second profile and a second mounted composer on the positive side; a page Stop, a turn Stop, voice controls, a hidden stale Stop and a finished answer on the negative side.
- PACK no longer fails `FAILED_VERIFY` with "archive member written more than once" when a project carries its own untracked generated manifest (SRC-100). A reserved archive-control name — `.audapack/manifest.json` or `_AUDAPACK_MANIFEST.json` — is a path AUDAPACK writes itself, so a source file sitting on one is never ordinary payload. That rule was applied to the TRACKED leg only, and the UNTRACKED leg of `build_git_inventory()` never looked at the reserved names at all. The state that exposed it is the ordinary one: a project that packs once and never commits the result has an untracked, non-ignored `.audapack/manifest.json`, which was classified as ordinary JSON, entered `included_entries()`, was written by the payload writer and then written AGAIN by the control writer. The duplicate was caught only by post-write parity verification, so the operator got a duplicate-name error naming neither the cause nor the file. One classification now governs both origins: a control artifact carrying AUDAPACK's own marker, on a name this pack regenerates, is superseded — the fresh artifact replaces it, the source copy is recorded as a named omission, and the worktree is never touched. The entry keeps its real `origin` (tracked stays tracked, untracked stays untracked) and its real frozen evidence — size, mtime, inode — instead of a size-0 placeholder, so a file the operator can no longer see in the archive stays measurable and counts toward `excluded`, never `included`. Arbitrary, malformed or project-owned bytes on a reserved name still fail closed in BOTH origins, and the refusal no longer claims the file was tracked: a new `RESERVED_ARCHIVE_NAME_CONFLICT` code replaces `TRACKED_RESERVED_ARCHIVE_NAME_CONFLICT` for untracked and filesystem sources, whose messages already said "Source path" while the code pointed operators at a repository that is not involved. A pre-write ownership assertion now refuses the collision before a single archive byte is written, rather than after a staging ZIP has already been filled with the first copy; the post-write duplicate check stays as defense in depth, and neither suppression of zipfile's duplicate warning nor weakening of `verify_inventory_archive()` was used.
- A finished ChatGPT audit response no longer stays BUSY forever, so A3 wave progression resumes (widget 0.0.85). The live FastPrompter A3 stall was not a label defect: an enabled A3 runtime sat at BUSY with a visibly terminal response (final response actions mounted, "Worked for 13m 50s", no real generation Stop on screen) and the campaign stayed at 0/3 forever, because `chatGPTIsGenerating()` returned true and short-circuited `evaluateAutoAudit()` **before** `completedAssistantCandidate()` — no SAVE, no wave commit, no next wave. Two things produced that false positive: `CHATGPT_STOP_SELECTOR` carried the wildcard `button[data-testid*="stop" i]` (plus a bare `button[aria-label="Stop"]`), and the match was accepted on `chatGPTSendNearComposer()`, a **Send-discovery** predicate whose 7-level ancestor walk above the prompt editor accepts essentially any visible element in the bottom page shell. Generation is now a single authority, `chatGPTGenerationSnapshot()`, consumed identically by the compact label, the audit evaluator, the observer, worker cleanliness and Send availability, so no layer can claim "generating" while another claims the response is terminal. A generation Stop must satisfy **both** halves: an exact canonical identity (`[data-testid="stop-button"]`, `aria-label="Stop generating"`, `aria-label="Stop streaming"`) **and** proven ownership of the *current* composer — inside the composer root, or in the composer form's own parent shell when that shell carries the composer's Send control. Voice, dictation, media and response-action controls are excluded, a shared ancestor higher up the page is no longer ownership, and a control from a stale composer shell has no live Send sibling to prove it. The broad shapes survive only as a diagnostic name: a visible stop-shaped control beside a finished response is reported as `stale_stop_candidate_ignored` and never obeyed. The genuine Chrome transition — final-action chrome mounted while the Stop control is still being removed — is held as `stabilizing` for a bounded 2.5 s window so no wave commits on a single frame of overlapping chrome; if the contradiction outlives that window the widget raises an explicit `generation_truth_conflict` and shows `ATTN` instead of lying about activity forever, and while truth is unresolved it sends nothing, stands no worker down and reloads nothing. Final response actions only ever *correct generation detection*: `completedAssistantCandidate()`, the response gate, stabilization, SAVE requirements and lineage identity remain the only authorities that commit a wave, and a "Stopped thinking" answer is still `interrupted` — not generating and not complete are two different facts.
- An explicit operator A3 OFF on a managed worker no longer leaves a zombie `AUDIT 0/3` lane on the Bridge (widget 0.0.84). Widget 0.0.83 made A3 ownership authoritative — a live non-terminal managed dispatch outranks a stale local `enabled=false`, and only a real human interaction records an operator stop — but it stopped at the local half. `setAutoAuditEnabled(false, { operator: true })` recorded the operator intent, cleared the A3 intent, released the local lease and stopped local monitoring, and never told the Bridge. The lane kept reporting `AUDIT 0/3` / `worker Chrome #N` for a campaign nobody was running: the widget legitimately refused to re-arm while the Bridge legitimately kept waiting, and that worker stayed pinned out of the pool behind `lease-still-owned` with no run left to protect. Explicit operator OFF is now an end-to-end managed action. When the window holds a valid managed dispatch and the dispatch is non-terminal, the widget issues ONE canonical `POST /v1/browser/jobs/{dispatch_id}/abandon` — the Bridge's existing operator-abandon semantic, terminal `FAILED` with `operator_abandoned`, which releases the lease so the lane stops occupying capacity, keeps the record in Audit Runs history with its post-start lineage, and never re-leases or re-STARTs the dispatch. `CANCELLED` is deliberately not used: it asserts that no Core was sent and is illegal from `AUDITING`, so choosing it would have refused exactly the state this fix exists for. A repeated OFF click, a reload after the acknowledgement, or a reload that resumes an unacknowledged stop never produce a second, contradictory transition — `abandon_job` returns a terminal job unchanged and the local retry budget is capped at 3. When the stop cannot be delivered, local operator intent stays authoritative (A3 stays `OFF`) but the widget says `ATTN` with a durable `a3OperatorStopPending` carrying `dispatch_id` / `campaign_run_id` / `worker_id` / `conversation_key` / previous and resulting dispatch state, never ordinary `CHAT` — reading `CHAT` there would have been the same split brain in the opposite direction, claiming the campaign had ended while the Bridge still held the lane. The managed worker poll resumes a pending stop on every tick. Every internal disarm — route hydration drift, runtime migration, storage repair, worker stand-down, stale conversation-key repair, managed recovery — still passes `{ operator: false }` and stays local and repairable; only a human decision retires a managed run. An unmanaged chat with A3 OFF is unchanged local-only behaviour.
- A hydrating audit turn that finishes authoring purely through `characterData` still gets its guaranteed second reconciliation (widget 0.0.82). The 0.0.81 escalation only armed `characterData` observation once `liveAuditActivitySnapshot().active` was true, and `active` requires a classifiable audit user turn — so during route hydration, when the audit user turn node already exists but its authored text is not yet complete enough for `classifyAuditTurn()` while ChatGPT is already generating, the observer stayed on the childList-only `turns` config and a stream arriving only as `characterData` on the existing node never re-armed `reconcileEnabledIdleAuditRuntime()`. Now enabled + idle + generating opens a BOUNDED characterData recovery window (`hydrationRecoveryWindowOpen`, hard-capped by `AUTO_HYDRATION_RECOVERY_WINDOW_MS`) even before lineage is recognizable: during the window the observer escalates to `stream`, a characterData-only hydration re-arms canonical reconciliation, and the widget adopts the correct `wait-<wave>` (Core and every non-Core profile wave) with no manual Resume, no page click and no new turn node. The window is only permission to keep looking briefly, never an adoption: ordinary non-audit generation rides it harmlessly (reconciliation refuses it, the label stays `BUSY`, never `READY` and never a wave) and it collapses back to the cheap `turns` config the instant generation ends, the runtime is adopted, auth/quarantine occurs, or the cap expires. The existing `reconcileEnabledIdleAuditRuntime` / `resumeRuntimeFromAuditTurn` path stays the single runtime-adoption authority; no parallel recovery state machine was added.
- A visibly generating ChatGPT audit is never labeled `READY` (widget 0.0.81). Live on 2026-09-28: several audit chats were actively streaming (Core turn on screen, ChatGPT Thinking / Stop generating showing, A3 enabled) while the compact widget read `READY`, because `superCompactAutoLabel()` derived `READY` from a stored `idle`/`complete` runtime without first applying live-generation truth, and the idle observer sat on a childList-only `turns` config so a response that streams as `characterData` after a hydration miss never re-armed reconciliation. Live activity now outranks passive stored readiness: a cheap `chatGPTIsGenerating()` probe gates the label, and while ChatGPT is generating the widget shows the active wave — `CORE` / `W2` / `PERF` for Quick3 and profile-aware `W1`..`Wn` for Super10 and every other wave (`compactWaveToken`), or a neutral `BUSY` for ordinary non-audit generation, never `READY` and never a hardcoded fallback. Generation detection matches current ChatGPT topology: the Stop control is found inside the composer or in a composer-adjacent sibling shell outside the `<form>` using the same proximity fence as the Send path (`chatGPTSendNearComposer`), so an unrelated Stop button elsewhere on the page is not mistaken for generation. A new read-only `liveAuditActivitySnapshot()` reuses `classifyAuditTurn` and the profile-aware lineage to decide whether an audit is genuinely in flight without mutating runtime; the enabled+idle observer temporarily escalates to `stream` while that snapshot is active and stays cheap on genuinely idle chats and on ordinary generation. An attached ZIP tile no longer masks a live audit, and ordinary non-audit generation is never adopted as an audit runtime. The existing `reconcileEnabledIdleAuditRuntime` / `resumeRuntimeFromAuditTurn` path stays the single runtime-adoption authority; no parallel state machine was added.
- A3 no longer dies in `BLOCKED PRE-START` with one opaque `file-injection-rejected` for every project (widget 0.0.80). The trigger was confirmed live: the 2026-09 ChatGPT build changed the composer DOM itself. The prompt editor dropped its `#prompt-textarea` id and its `aria-label` went from `Chat with ChatGPT` to `Ask ChatGPT`, keeping only the `ProseMirror` contenteditable; the composer `<form>` lost `data-type="unified-composer"` and now carries only hashed `Composer*` layout classes; and the composer mounts THREE hidden `image/*` and `image/*,video/*` file inputs beside the one general input. The old editor and root selectors matched none of this, so `chatGPTComposerRoot()` returned null and every A3 lane blocked before it could even look for the upload input. Editor discovery now also matches `[contenteditable="true"][role="textbox"].ProseMirror` and `aria-label^="Ask ChatGPT"`; root discovery accepts a `[class*="Composer"]` shell; and the upload engine rejects media-only inputs (`accept` listing only image/video/audio types) so a project ZIP or a generated `.md` prompt is never injected into an image or video picker and the three-input build disambiguates to the single general input. Verified by CDP against the real logged-in chatgpt.com managed profile: composer found, `chatGPTUploadSurface()` returns `composer-input`, and `injectComposerArchiveFile()` delivers the archive to the general input. On 2026-09-27 a six-project A3 launch produced six identical `BLOCKED PRE-START` rows at 0/3 waves, every managed ChatGPT window sitting on a clean root chat with no ZIP tile and no Core turn sent. The Bridge held a valid archive for all six, so the bytes were not the problem: delivery stopped at the composer's file input. Two defects sat in one place. Discovery accepted only a file input rendered *inside* the composer root (`#upload-files[type=file]` or `input[type=file][multiple]`), and every caller additionally demanded `root.contains(input)` on top of that, so a current ChatGPT build that renders the input in a body-level attachment portal, mounts it only after the `+` control opens, or drops the `multiple` flag, was invisible and indistinguishable from "no input at all". And missing input, missing composer root, a detached input and a refused FileList assignment all reported the same code, so a retry could never learn anything and the whole pre-start budget was spent before the lane gave up. Discovery is now semantic and bounded: a stable upload id/testid proven to belong to the live composer first, then the composer's own inputs, then a portal input the composer itself declares through `aria-controls`/`aria-owns` or that shares one marked shell. Ambiguity fails closed, conversation turns and settings/profile/avatar pickers are never candidates, a stale SPA composer is never a candidate, and more than 12 file inputs on the page is an outright refusal. When the input is genuinely absent, one canonical preparation step opens the composer's own attachment surface, waits boundedly for the input, assigns the FileList and closes the menu again -- it selects no tool, types nothing and never sends. Injection reacquires the live composer root and the live input, proves ownership, and retries once across a React remount. Failures now carry their own code: `upload-input-unavailable`, `composer-root-unavailable`, `upload-input-ambiguous`, `upload-input-detached`, `file-injection-rejected`, with `attachment-registration-timeout` and `attachment-identity-mismatch` already distinct. A structural verdict (`...unavailable`, `...ambiguous`, `composer-root-unavailable`) blocks ONCE with the observed composer shape appended, instead of burning five retries per lane; a remount or a refused assignment stays retriable and keeps its code. Copy Details on the Audit Runs row now shows the exact reason, the short code plus a bounded, content-free observation (`composer=form attach=1 file_inputs=0 verdict=... inputs=[...]`), and the same shape is reported to the Bridge on every worker heartbeat, so a build that moved its file input is readable evidence rather than a guess from a screenshot. The manual ZIP door and the A3 worker door use the one engine; there is no second upload implementation.
- A Git-tracked AUDAPACK-generated archive control artifact is superseded instead of blocking the pack forever. The reserved-name refusal above is right for a project-owned file, but it also caught the one case where the tracked file IS the artifact AUDAPACK wrote on an earlier pack: `_ZAICODE` has a committed `_AUDAPACK_MANIFEST.json` (7649 bytes, `product: AUDAPACK`, `project: _ZAICODE`), so that project could not be packed again without a human running `git rm --cached` by hand. Packing now supersedes it: the freshly generated control artifact carries the archive, the tracked stale copy is recorded as a named omission (`superseded_control` in `.audapack/manifest.json`, counted as excluded, never included and never silent), and the pack log names the path and the `git rm --cached` line that clears it. The supersession is narrow on purpose — only a reserved name THIS pack regenerates is a candidate, and only when the bytes parse as a JSON object carrying AUDAPACK's own marker for that name. A hand-written file on a reserved name, an unparseable one, a read error, or the legacy `_AUDAPACK_MANIFEST.json` when the manifest is disabled all keep the existing fail-closed `TRACKED_RESERVED_ARCHIVE_NAME_CONFLICT`; secrets and private keys keep the hard-safety classification untouched. The worktree is never modified: a superseded file is still there, byte for byte, and the last good archive is still the rollback authority.
- A Git-tracked file sitting on an AUDAPACK reserved archive-control name is reported as the collision it is, not as hard safety. Packing `_ZAICODE` failed with `[FAILED_INVENTORY][TRACKED_HARD_DENY_CONFLICT] tracked path matches the hard-safety deny policy` for a tracked `_AUDAPACK_MANIFEST.json` — a path AUDAPACK itself writes as generated archive metadata — which sent the operator hunting for a credential that was never there. The refusal is unchanged and still fail-closed (no archive byte, tracked source never silently omitted, `tracked` file never overwritten, the last good archive untouched), but it now classifies as `TRACKED_RESERVED_ARCHIVE_NAME_CONFLICT` and says what to do: `Tracked source path '_AUDAPACK_MANIFEST.json' conflicts with an AUDAPACK reserved archive metadata path. Remove it from source control or rename the project-owned file before packing.` Secrets and private keys keep the existing hard-safety classification and message. `PackResult` carries the exact code alongside its status bucket, and Project Room shows one canonical line — project name, `[STATUS][CODE]`, the conflicting relative path and the remediation — in the status bar and in the row's ⓘ detail popup.
- The widget's ZIP no longer waits behind the managed worker windows (widget 0.0.70). The userscript manager queues every window's requests together, and each worker kept a `/v1/browser/poll` request open for up to ~6 s (six workers, 75 s TTL). The operator's own archive ensure and download queued behind those polls: the diagnostics log showed `GET split hdr 37.57s` and a 38 s "ensure" for an archive that was reused as-is, against 3 ms of Bridge work. Workers now poll with `wait_seconds: 0` and wait out the 2 s idle gap in a local timer that holds no request, so a claimable job is still picked up within about 2 s.
- A manual ZIP no longer ends in `SEND_TIMEOUT` while ChatGPT is still uploading a large archive (widget 0.0.70). ChatGPT shows no progress spinner for that upload, so the tile looked ready while Send stayed disabled, and the shared Send wait gave up after 1.4 s of that. Two of the three ZIPs in the diagnostics log (40 MB each) failed this way with `send_ready_ms` of about 1.5 s. The operator's ZIP now waits for its whole Send budget, raised from 12 s to 30 s. The wait still returns as soon as Send is ready. Automated callers keep the short early exit, so a dead composer never holds a worker lane.
- The test suite no longer hangs or opens real agent consoles. A static `QMessageBox` in a headless run waited forever for a click (`test_launcher_focus_reuse.py`, `test_project_double_click.py`). Launch tests that patched only `main_window.OpenCodeLaunchPolicy` let the real admission fall back to a real degraded OpenCode console: 44 PowerShell, cmd and OpenCode processes from test temp directories were found running after suite runs. `tests/conftest.py` now answers static message boxes at once. Its existing process-boundary guard, which already refuses browsers, now also refuses `-NoExit` consoles and OpenCode/agent launchers and names the offending test at session end. `tests/ui_qt/conftest.py` gives placeholder project paths a plain unmanaged admission. The five managed-launch tests now stub admission where the window calls it, mark their roots as SAIPEN-managed and wait for the off-thread preflight that T-216 introduced.
- Packing a live non-Git project no longer fails with `[FAILED_INVENTORY] [SOURCE_INVENTORY_INCONSISTENT] source traversal incomplete` just because the project's own tooling removed a directory during the walk (agent session, exec and lock directories under a running tool's runtime folder). A directory or file that disappears between its parent's listing and its own read no longer exists, so it is counted as `vanished_entries` instead of a traversal failure; a directory Windows still reports as delete-pending ("access denied") is re-probed once. A genuinely unreadable directory, and a missing source root, still fail the pack, and the failure now names the first path that could not be read. A pack that fails because a file changed under the writer (`FAILED_SOURCE_CHANGED`) or could not be read now names that file too.
- The manual ZIP "GET..." phase can now say where its time goes. The archive download reports headers, first body progress, body complete, byte materialization and browser SHA-256 separately (passive `GM_xmlhttpRequest` callbacks, no extra request), the Bridge returns `X-AUDAPACK-Archive-Prep-Ms`, `X-AUDAPACK-Archive-Digest-Ms` and `Server-Timing` for its pre-stream work, the browser hash shows as `VERIFY...` instead of `GET...`, and a busy phase shows its elapsed time after 0.7 s (`GET 1.8s`). The full split rides the `delivery_timing` record that is mirrored to `logs/widget_diagnostics.log`.

## 0.3.0 - 2026-09-05

### Added
- Audit fidelity profiles. Packing now runs under one of four declared profiles — COMPACT, STANDARD (default), DEEP, FULL — each with a soft byte budget (10 / 30 / 100 MB, uncapped) and per-directory media sampling. An archive is now explicitly either an *audit representation* (COMPACT/STANDARD/DEEP) or a *full snapshot* (FULL), and the manifest says which: `fidelity_profile`, `archive_semantics`, `budget_bytes`, `budget_met`, per-reason exclusion totals, `largest_omitted`, `pruned_directories` and a `media_inventory` that reports every media group it saw — exact file counts and byte totals per directory and media class, plus a bounded sample of the kept and omitted filenames. Profile, byte cap, sample counts and `always_include`/`always_exclude` overrides are configurable (`config.example.json`, Settings dialog).
- The budget is deliberately soft: mandatory audit material (code, tests, configs, manifests, schemas, build/runtime-referenced assets and anything named in `always_include`) is never trimmed to reach a target. A source-heavy project overshoots its profile budget and the manifest declares `budget_met: false` rather than silently dropping source.
- INAUDIT rename and routing actions. Layers renumbers an audit layer through an exclusive create that never overwrites an existing `audit/N.md` and refuses a number already taken; Inbox renames a capture's title in place. A capture can be routed before assignment: **Pin project** records the operator's own target and outranks the classifier's guess everywhere it is displayed, and **Assign** refuses an unregistered project or an already assigned capture instead of writing twice.
- The project-row double-click is now the operator's choice (`project_double_click_action` / `project_double_click_launcher_id`): open the preferred launcher, the project folder, INAUDIT, Instances, a terminal, the archive folder, the audit folder, or nothing. The default is **open the preferred launcher** (OpenCode), the action is set per row-kind and stored as a stable value — never a translated label — and the launcher is stored by ID so reordering launchers cannot change it. A deleted or disabled launcher reports `Double-click launcher unavailable: <id>` instead of silently starting another agent. Group headers still expand/collapse and empty slots still open Add Project, and the launcher action reuses the one launch path, so a double-click focuses an existing instance rather than spawning a duplicate. An existing config that explicitly stores `inaudit` keeps the historical INAUDIT behaviour; a missing or unknown value migrates deterministically to `launcher`.

### Fixed
- **A title-integrity feature could break every other subprocess spawn (T-210, escaped regression of T-209/T-198).** T-209's resolver found a managed console by calling `kernel32!AttachConsole` → `GetConsoleWindow` → `FreeConsole` from inside the long-lived `pythonw` host — on `register`, on the 1000 ms heartbeat, on the unknown-HWND WinEvent path and on refresh. Those calls act on the **calling process**, not on a thread: attaching repopulated AUDAPACK's own standard handles with the target console's, and freeing left those values behind as stale handles, so the very next `subprocess.run(..., capture_output=True)` failed at process creation with `[WinError 6] The handle is invalid` — permanently. That is why Project Room → OpenCode → **Fleet preflight** then refused every managed project with `SAIPEN Fleet preflight failed: [WinError 6] The handle is invalid`. No process-global console API remains in production, and a static proof fails the build if one comes back. Discovery is a read-only `EnumWindows` scan — the launch PID's own visible windows plus AUDAPACK's own unguessable launch correlation token — `InstanceMonitor` stays the HWND authority and ownership transfers through `bind_hwnd`, a completely generic title is only drift once ownership is mechanically established, and the heartbeat asks the monitor for a fresh correlation **only while a binding is missing**, so a healthy tick never re-scans the desktop. T-209's title restoration, the WinEvent hook, the 1000 ms heartbeat with zero-instance stop and the configurable project-row double-click are all unchanged. This also corrects T-209's assumption that a managed console window's owner PID is conhost's: on this platform Windows attributes the `ConsoleWindowClass` window to the process that launched it, which is why the plain PID scan is now sufficient. The bound Fleet preflight and the other non-interactive SAIPEN machine calls pass `stdin=subprocess.DEVNULL` as defense in depth. A native `pythonw` red control reproduces the handle mutation and the real `WinError 6` from the pre-fix code, and the corrected `pythonw` worker keeps its NULL host handles while running 100 real Fleet preflights and 100 real child spawns with four managed titles drifting underneath.
- Managed console titles survive the whole instance lifetime (T-209, escaped regression of T-205): the guardian resolved `GetConsoleWindow` through **user32**, which does not export it, so every real launch raised `AttributeError` inside HWND resolution, cached an empty window set and never restored a title — and the WinEvent hook then asked kernel32 for `PostThreadMessageW` (a user32 export) and failed to install at all. All native entry points are now bound once, explicitly, in their owning DLL. An event for an HWND nobody has mapped yet is no longer discarded: it drives a bounded slow path over the active registrations only (the console window's PID is conhost's, so `window_pid` can never answer for it). A 1000 ms **title-integrity heartbeat** runs while — and only while — a managed instance exists and restores drift even if every WinEvent is missed; with zero instances the timer and hook are released, so there is no permanent poller. `InstanceMonitor`'s proven `launch_pid + hwnd + correlation token` association is fed into the guardian with `bind_hwnd`, and ownership carries the launch PID, creation token, generation, exact HWND and native window PID so a reused HWND can never be renamed. `Audit folder`/`Audits root` handlers no longer read a non-existent `audits.root_dir`.
- Packing accounting no longer goes quietly false on an unusual tree. The identity `discovered == included + excluded + failed` now holds across symlinked files, unreadable entries and untraversable directories, and a partly enumerated tree is declared with `walk_incomplete` instead of being presented as complete accounting. The symlink probe is itself a `stat`, so before this an EACCES file escaped the per-file guard, ended the whole walk, and reported an empty tree as a valid audit representation.
- Bridge status endpoints stop re-deriving per-request state: the agent-state stamp uses a request-local `(root, binding)` memo, `invalid_auth` compaction runs under canonical proof with byte-identical token-replacement recovery, index writes are membership-only, and job pruning keeps sole copies under a 400-job bound.
- The Project Room `IA` badge now tells the truth about pending captures. Three defects stacked: the INAUDIT snapshot was rebuilt before the project dictionary it iterates was repopulated, so a fresh room snapshotted nothing and every badge read 0 until the operator opened an inbox by hand; the pending count read only the classifier's suggestion, hiding every hand-pinned capture; and the delegate drew the badge only for a non-zero count, so the surface that was supposed to report the queue disappeared exactly when it was empty and gave no way to tell "no captures" from "not computed".
