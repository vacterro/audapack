[P1] [W2-001] audapack/prepared_worker.py:PreparedWorker.stop / audapack/bridge/server.py:run_bridge_server shutdown ownership

EVIDENCE:
- `PreparedWorker` owns one scheduler thread plus two executors:
  - `_pool = ThreadPoolExecutor(max_workers=3, thread_name_prefix="prepared-launch")`
  - `_probe_pool = ThreadPoolExecutor(max_workers=3, thread_name_prefix="limit-probe")`.
- `stop()` currently does:
  1. `_stop.set()`
  2. wakes the scheduler
  3. joins `_thread` for at most 5 seconds
  4. calls both executor shutdowns with `wait=False, cancel_futures=True`
  5. returns `None`.
- `cancel_futures=True` cancels queued futures only. Already-running executor functions are deliberately not waited for by `wait=False`.
- The launch executor carries irreversible prepared operations, not merely reads:
  - `_deliver`
  - `_deliver_audit`
  - `_deliver_sync`
  - `_deliver_prime`
  - recovered delivery resumption.
- `_deliver` can create an external CLI process and feed its payload.
- `_deliver_audit` enters `AuditRunCoordinator.start()` under the durable `source_execution_id`.
- sync/prime delivery paths also advance durable execution state and perform external launch/delivery work.
- `run_bridge_server()` calls `prepared_worker.stop()` and immediately continues to supervisor shutdown, `server.server_close()`, and `remove_pid(...)`.
- The neighboring `DispatchSupervisor.stop()` already implements the stronger contract this worker lacks: it waits for the active pass, returns a truth value, retains truthful thread ownership until exit, and `run_bridge_server()` explicitly checks that result.
- Read-only reproduction against the supplied implementation submitted one already-running function into `PreparedWorker._pool`, blocked it on an Event, called `stop()`, and observed:
  `STOP_RESULT None`
  `STOP_SECONDS 0.0`
  `FUTURE_DONE_AFTER_STOP False`
  `DELIVERY_FINISHED_AFTER_STOP False`
  After releasing the function:
  `DELIVERY_FINISHED_EVENT True`
- Therefore `PreparedWorker.stop()` had already returned while work owned by the prepared worker was still alive and later completed.
- There is a second race inside the same root cause: if the scheduler thread itself fails to join within five seconds, `stop()` still shuts its executors and returns. That still-running tick can subsequently reach one of several `_pool.submit(...)` / `_probe_pool.submit(...)` sites against a shut-down executor.
- Existing prepared-worker tests exercise `stop()` as cleanup but contain no barrier regression comparable to `tests/test_dispatch_supervisor.py`'s "no launch after shutdown request" proof.

DEFECT:
Bridge shutdown is not an ownership barrier for prepared work. The Bridge can close its HTTP server and delete its PID ownership record while an already-running prepared launch/audit/sync/prime action still executes. This creates a split-brain lifecycle: externally visible Bridge ownership says the process is gone while its prepared side effects continue.

The same implementation can also tear executors down underneath a scheduler tick that exceeded the five-second join, turning shutdown timing into `cannot schedule new futures after shutdown` failure drift.

This is particularly dangerous for prepared AUDIT and agent launch paths because the late work is exactly the kind of side effect the surrounding scheduler/receipt machinery is designed to execute once.

REPAIR:
- Give `PreparedWorker.stop()` a truthful barrier contract analogous to `DispatchSupervisor.stop()`.
- Track scheduler-thread liveness and submitted delivery/probe futures explicitly.
- Once shutdown begins:
  - reject all new prepared submissions;
  - wake and stop the scheduler loop;
  - cancel work that has not begun;
  - prevent every post-stop `_pool.submit` / `_probe_pool.submit`;
  - wait for already-running side-effectful work to reach a defined safe terminal/recovery boundary before declaring quiescence.
- Do not pretend a Python future that has already started can be cancelled. Running delivery needs cooperative shutdown checks at boundaries before irreversible work where cancellation is still safe.
- Once an irreversible side effect has begun, preserve its durable receipt and either finish/adopt it or expose a truthful non-quiescent shutdown result; never silently orphan it.
- Make `stop()` return success/failure (or an equally explicit lifecycle state).
- Do not clear/lose the thread handle while it is still alive.
- Update `run_bridge_server()` so `server_close()` and PID removal happen only after prepared ownership is genuinely quiescent, or so a failed quiescence gate is surfaced and ownership remains truthful.
- Preserve the current exactly-once/recovery semantics. Shutdown hardening must not manufacture a second launch to compensate for an uncertain first launch.
