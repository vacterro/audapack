- `_worker_profile_is_live()` claims to determine whether the dedicated worker profile/window is live.
- Its actual implementation asks `BridgeService.browser_status()` and reduces that state to `dispatch.active_workers > 0`.

DEFECT:
A generic bridge worker count is used as a proxy for a specific managed-profile lifecycle fact. An unrelated worker can suppress the profile launch, while a valid newly launched profile without an installed widget may never satisfy the predicate intended to confirm that launch. REPAIR:

  1. managed/dedicated browser profile process or window is alive;
  2. widget worker from that managed profile is registered and bridge-ready.
- Base launch suppression/warm-up on an actual managed-profile process/window ownership signal, not aggregate `active_workers`.
- If bridge workers carry managed-profile identity, expose/count only verified managed-profile workers for the second predicate.
- Do not require the not-yet-installed userscript to prove the browser profile launched successfully.
- Add real predicate tests with foreign worker only, managed profile only, managed+widget, and no-worker states.

VERIFY:
1. Foreign/personal worker active, managed profile absent => installer must not consider dedicated profile live and must launch it.
2. Managed profile process alive before widget registration => launch predicate is true without requiring userscript registration.

ISSUE:
